ТЕСТЕРИ ДЛЯ ПЕРЕВІРКИ РОЗВ'ЯЗКІВ — ІНСТРУКЦІЯ
================================================

Що це
-----
Для кожної з 120 задач (40 EZ + 40 MED + 40 HARD, по темах 1-8) є окремий
тестер *_tester.cpp. Кожен тестер:
  - містить власний еталонний розв'язок задачі та генератор тестів;
  - генерує 100 тестів за обмеженнями задачі (для перших 1-2 тестів — фіксовані
    приклади з умови, решта — випадкові);
  - компілює ваш розв'язок (.cpp-файл або текстовий файл із кодом);
  - запускає його на кожному тесті з обмеженням часу (TL з умови задачі);
  - порівнює вивід з еталоном точним порівнянням рядків (ігноруючи кінцеві
    пробіли в рядках і порожні рядки в кінці виводу, та відмінності CRLF/LF);
  - друкує вердикт по кожному тесту: OK / WA / TL / RE, та підсумок.

Структура архіву
----------------
common/tester_common.hpp   - спільна інфраструктура (компіляція, запуск з
                              таймаутом, порівняння виводу)
common/tester_main.inc     - спільний main(), підключається в кінці кожного
                              *_tester.cpp

ez_problems/<тема>/EZ_<алгоритм>_tester.cpp    - легкі задачі
med_problems/<тема>/MED_<алгоритм>_tester.cpp  - задачі середньої складності
hard_problems/<тема>/HARD_<алгоритм>_tester.cpp - складні задачі

Теми (як у вихідному архіві задач):
  1_poshuk_ta_masyvy             - пошук та техніки на масивах
  2_sortuvannia                  - сортування
  3_matematyka                   - математика та теорія чисел
  4_zhadibni                     - жадібні алгоритми
  5_grafy                        - графи: обходи та найкоротші шляхи
  6_dynamichne_programuvannia    - динамічне програмування
  7_riadkovi_algoritmy           - рядкові алгоритми
  8_struktury_danykh             - структури даних та дерева

Як використовувати
-------------------
1. Скомпілюйте потрібний тестер (з тим самим стандартом C++17):

     g++ -O2 -std=c++17 -o EZ_linear_search_tester EZ_linear_search_tester.cpp

   Тестер шукає common/tester_common.hpp і common/tester_main.inc за
   відносним шляхом ../../common/ — тому НЕ переносьте *_tester.cpp окремо
   від цілої структури тек, або скопіюйте папку common/ поруч у тому самому
   відносному положенні.

2. Запустіть тестер, передавши йому розв'язок:

   а) якщо розв'язок лежить у файлі .cpp:
        ./EZ_linear_search_tester /шлях/до/solution.cpp

   б) якщо є лише текст коду в текстовому файлі (наприклад, скопійований
      код без розширення .cpp):
        ./EZ_linear_search_tester /шлях/до/solution.txt --source

3. Додаткові прапори:
     --quiet         компактний вивід (рядки символів: . = OK, W = WA,
                      T = TL, R = RE) замість рядка на кожен тест
     --seed N        змінити сід генератора тестів (за замовчуванням
                      фіксований - однакові тести при повторному запуску)

Приклад повного циклу:
  cd ez_problems/1_poshuk_ta_masyvy
  g++ -O2 -std=c++17 -o EZ_linear_search_tester EZ_linear_search_tester.cpp
  ./EZ_linear_search_tester /шлях/до/мій_розвязок.cpp --quiet

Вердикти
--------
  OK  - тест пройдено (вивід точно збігається з еталоном)
  WA  - неправильна відповідь
  TL  - перевищено ліміт часу (програма не встигла за TL з умови задачі)
  RE  - помилка виконання (ненульовий код виходу або crash/сигнал)
  CE  - помилка компіляції вашого розв'язку (показується лог компілятора)

Примітки щодо конкретних задач
-------------------------------
- Топологічне сортування (TOPOLOGICAL_SORT) у звичайному випадку має кілька
  правильних відповідей. Щоб точне порівняння рядків було коректним, EZ-тести
  будують графи з ГАРАНТОВАНО унікальним топологічним порядком; MED-тест
  вимагає саме лексикографічно найменший порядок (однозначна відповідь).
- Валютний арбітраж (HARD bellman_ford) використовує дійсні курси; щоб
  уникнути проблем точності на межі YES/NO, тести побудовані явно
  однозначними (помітний прибутковий цикл або повна відсутність циклів).
- Усі задачі з кількома запитами в одному тесті виводять відповіді по одній
  в рядку.

Усі 120 тестерів самоперевірені: для кожного написано окремий коректний
розв'язок, який підтверджено отримує ACCEPTED (100/100 OK) на 100
згенерованих тестах.


ПІДТРИМКА ІНШИХ МОВ ПРОГРАМУВАННЯ (мультимовні тестери)
========================================================

Окрім C++-версій (*_tester.cpp, описаних вище), для кожної з 120 задач є
ідентична за логікою МУЛЬТИМОВНА версія: *_tester_multilang.cpp. Вона
відрізняється лише тим, як готується й запускається розв'язок користувача —
сам генератор тестів та еталонна відповідь у задачі НЕ змінюються.

Підтримувані мови розв'язку (визначаються за розширенням файлу):
  .cpp, .cc, .cxx  -> C++      (g++ -O2 -std=c++17)
  .c               -> C        (gcc -O2 -std=c17)
  .py              -> Python   (python3, без компіляції; перевірка синтаксису
                                 через py_compile перед запуском)
  .js, .mjs        -> JavaScript (node; перевірка синтаксису через --check)
  .ts              -> TypeScript (tsc -> .js -> node)
  .java            -> Java     (javac -> java; ім'я класу визначається
                                 автоматично з "public class XYZ" у коді)
  .cs              -> C#       (mcs/Mono -> mono)
  .go              -> Go       (go build)
  .rs              -> Rust     (rustc -O)
  .php             -> PHP      (php; перевірка синтаксису через php -l)

Як використовувати:
    g++ -O2 -std=c++17 -o EZ_linear_search_tester_multilang \
        EZ_linear_search_tester_multilang.cpp
    ./EZ_linear_search_tester_multilang /шлях/до/solution.py --quiet
    ./EZ_linear_search_tester_multilang /шлях/до/Solution.java --quiet
    ./EZ_linear_search_tester_multilang /шлях/до/solution.go --quiet

Прапор --source тут НЕ підтримується (на відміну від звичайних *_tester.cpp):
мова визначається саме розширенням файлу, тому потрібен файл із правильним
розширенням, а не довільний текстовий файл з кодом.

Додаткові файли мультимовної інфраструктури:
  common/language.hpp              - визначення мови, компіляція/підготовка
  common/tester_main_multilang.inc - мультимовний аналог tester_main.inc
  generate_multilang.sh            - скрипт, яким згенеровано всі
                                      *_tester_multilang.cpp з оригінальних
                                      *_tester.cpp (запускати повторно лише
                                      якщо ви додасте нові задачі)

СТАТУС ПЕРЕВІРКИ ПО МОВАХ (у середовищі розробки цього пакета)
----------------------------------------------------------------
Середовище розробки мало встановлені: g++, gcc, python3, node, tsc.
НЕ було встановлено (мережа вимкнена, перевірити неможливо): javac (JDK),
mcs/mono (C#), go, rustc, php.

  C++         - ПОВНІСТЮ ПЕРЕВІРЕНО: ACCEPTED на правильному розв'язку.
  C           - ПОВНІСТЮ ПЕРЕВІРЕНО: ACCEPTED на правильному розв'язку.
  Python      - ПОВНІСТЮ ПЕРЕВІРЕНО: ACCEPTED на правильному розв'язку,
                CE на синтаксичній помилці.
  JavaScript  - ПОВНІСТЮ ПЕРЕВІРЕНО: ACCEPTED на правильному розв'язку,
                CE на синтаксичній помилці.
  TypeScript  - ПОВНІСТЮ ПЕРЕВІРЕНО: ACCEPTED на правильному розв'язку
                (попри відсутність @types/node), CE на справжній
                синтаксичній помилці.
  Java        - логіка коду коректна (екстракція імені класу перевірена
                окремо), але РЕАЛЬНУ компіляцію/запуск перевірити не
                вдалося - в середовищі є лише java (JRE), немає javac
                (JDK). На машині з повним JDK команда
                "javac -d <workDir> <ClassName>.java" та запуск
                "java -cp <workDir> <ClassName>" є стандартними й мають
                спрацювати без додаткових змін.
  C#          - НЕ ПЕРЕВІРЕНО (mcs/mono відсутні в середовищі розробки).
                Команда розрахована на Mono (mcs -> mono solution.exe).
                Якщо на цільовій машині є лише .NET SDK (dotnet) без
                Mono, команду компіляції потрібно замінити на створення
                міні-проєкту (dotnet new console + dotnet run) - однією
                командою mcs це не зробити, бо dotnet не компілює
                окремий .cs файл без .csproj.
  Go          - НЕ ПЕРЕВІРЕНО (go відсутній в середовищі розробки).
                Команда "go build -o <bin> <file>.go" стандартна для
                одиночного файлу пакета main і має спрацювати без змін.
  Rust        - НЕ ПЕРЕВІРЕНО (rustc відсутній в середовищі розробки).
                Команда "rustc -O -o <bin> <file>.rs" стандартна для
                одиночного файлу й має спрацювати без змін.
  PHP         - НЕ ПЕРЕВІРЕНО (php відсутній в середовищі розробки).
                Команда "php <file>.php" для запуску та "php -l <file>.php"
                для перевірки синтаксису є стандартними.

Якщо на цільовій машині якась команда виявиться відсутньою або з іншою
назвою (наприклад, замість "mcs" може знадобитися повний шлях, або замість
"go" - "go1.21"), достатньо відредагувати відповідний case у функції
prepareSolution() у файлі common/language.hpp - решта системи (genTest,
еталонні розв'язки, порівняння виводу, вердикти) ніяк не залежить від мови
і змінювати її не потрібно.
